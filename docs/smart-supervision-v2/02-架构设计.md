# DSH Smart Supervision v2 架构设计

> 状态：ADR-001～ADR-015 已批准（2026-08-27）；P0 已于 2026-08-28 按单独授权完成闭环，架构语义未改变，P1/P2 仍冻结。

## 1. 架构目标

本架构把 Supervisor 定义为 **Goal 的监督策略层**，而不是第二个 Goal Driver。stock Driver 对每个 Goal queue candidate 在 reservation 前触发最小 awaited policy seam；有 final completed turn 时 Supervisor 才评估/可选 Council，无 completed 时只绑定 pending delivery，并通过动态 runtime-context 只让目标 Goal Round 看到结论。

架构必须同时保证：

- 原生 Goal 生命周期、Goal Round prompt、准入计数和 activation 规则不变；只增加 fail-local policy seam 与 Goal 专属 runtime-context 不恢复到 human turn 的安全修正；
- active Goal 期间 Supervisor 不调用 `followup`、`steer` 或 `inject`；
- Supervisor、Role Core、GroupX、Identity Library 可分别卸载和降级；
- 模型可见监督上下文由会话日志重建；
- 学院与 Group 共享 RoleRef，但不共享 Actor 或运行状态；
- 旧 Store、分配、Handoff 和非 Goal 监管模式可恢复。

## 2. 所有权分层

```text
配置与定义层（版本化包）
  dsh-role-core definitions / Supervisor config / GroupX config
                              ↓
Host 权威服务层
  GoalService ── SupervisorPolicyService ── RoleCore ── CouncilService?
       │                 │                       │
       │                 └── SmartSupervisionStore
       │
  stock Goal Round Driver（唯一续行调度器）
                              ↓
模型上下文层
  goal/before-next-round → Assessment/Deliberation
  systemPrompt.context → durable runtime-context snapshot
                              ↓
通道层
  官方 Goal RPC + /dsh-supervisor/api/v2 + /_dsh/role-core/v1
                              ↓
Client 层
  官方 Goal UI + Supervisor additive panel + GroupX panel + Session Matrix
```

### 2.1 Host

Host 拥有跨会话 Role Registry、Supervisor policy、进展评估、停滞判定、讨论事务、预算、审计与持久化。Role Core 和 Supervisor 各挂载一次，不得由 Agent Preset 每会话重复注册进程级 Service。

v1 明确采用单 Host writer：`DshSmartSupervisionService` 在同一 Cordis Host 只能有一个实例，第二个 Loader row/HMR 重叠注册立即以 `SUPERVISION_INSTANCE_CONFLICT` 拒绝启动。更新必须先 drain/dispose 旧 fiber，再挂载新实例；不设计跨进程分布式 lease。每 session 的 Coordinator/generation 只处理同一合法 Host 实例内的并发。

### 2.2 Agent scope

Supervisor Host fiber 只注册一个全局动态 `systemPrompt.context()` provider，并按 `AssembleContext.agent` 查询 per-agent 状态；不为每个 Agent 重复注册 Service/provider。agent-local turn admission、generation 与 cancellation 状态按 exact Agent 管理，在 `agent/disposed` 和 Supervisor unload 两侧清理。

### 2.3 Client

Client 只展示 Host DTO 和发送明确操作。它不计算停滞、不持有预算、不解析 Prompt、不决定参与者、不保存 Goal 或讨论事务。

### 2.4 Agent Preset

本项目不通过 Preset 安装 Role Registry、Council Provider 或全局 Supervisor Service。Preset 可以继续决定 persona、工具与模型可见能力，但不是监管状态真源。

## 4. 核心数据合同

以下为逻辑 TypeScript 合同。实现时使用严格类型、边界验证与 branded id；字段名变更必须同步需求、测试和 API schema。

### 4.1 Role Core

```ts
type RoleKind = 'cognitive' | 'functional' | 'domain'
type RoleStatus = 'active' | 'deprecated'

interface RoleRef {
  id: string
  version: string
}

interface RolePrompt {
  identity: string
  objectives: readonly string[]
  mustCheck: readonly string[]
  mustNot: readonly string[]
  outputContract: readonly string[]
}

interface RoleDefinition {
  schemaVersion: 1
  ref: RoleRef
  namespace: string
  kind: RoleKind
  label: string
  shortDescription: string
  capabilityTags: readonly string[]
  responsibilities: readonly string[]
  outOfScope: readonly string[]
  acceptance: readonly string[]
  requiresRoleRefs?: readonly RoleRef[]
  lifecycle: {
    status: RoleStatus
    supersededBy?: RoleRef
  }
  presentation?: {
    icon: string
    accent: string
  }
  prompt: RolePrompt
}

interface PublicRole extends Omit<RoleDefinition, 'prompt'> {
  contributorId: string
  contributionVersion: string
  definitionDigest: string
}

interface ActorRef {
  authority: string
  id: string
}

interface RoleBinding {
  schemaVersion: 1
  actor: ActorRef
  slot: string
  role: RoleRef
  origin: 'manual' | 'automatic' | 'default' | 'migration'
}
```

`RoleDefinition.prompt` 只允许 Host 内部解析。HTTP、Client、日志、审计和消费者 Store 只能保存 PublicRole、RoleRef、RoleBinding 或 digest。

Role v1 协议常量固定如下，不作为可放宽的部署配置：

| 项目 | 规则/上限 |
| --- | --- |
| `RoleRef.id` | `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$`，最多 128 字符 |
| namespace / contributorId | 同类格式，最多 64 字符；role namespace 必须等于 contributorId 或以 `contributorId.` 开头 |
| version | 不透明精确标识，`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` |
| ActorRef | authority 最多 64、id 最多 128；禁止控制字符、路径和 secret 形态 |
| slot | 同标识格式，最多 64 字符；消费者 Store 内 `(authority,id,slot)` 唯一 |
| presentation | icon 为最多 64 字符的内建语义 ID，禁止 URL/路径；accent 必须为 `#RRGGBB` |
| 普通展示文本 | label 80、description 400、单数组 32 项、单项 500 字符 |
| Prompt | 单片段 2 KiB、单角色 32 KiB、单 contribution 256 KiB |
| 数量 | 每 contribution 最多 64 roles/aliases；全局 64 contributors、256 role versions |

一个 Actor 的多个角色使用多条原子 `RoleBinding` 表示，不在一条 binding 中塞入多个 RoleRef。`deprecated` 版本仍可解析已有/migration binding，但不能用于新的 `manual`、`automatic` 或 `default` binding。

### 4.2 Role contribution

```ts
interface RoleAlias {
  from: RoleRef
  to: RoleRef
  deprecatedSince?: string
}

interface RoleContribution {
  schemaVersion: 1
  contributorId: string
  version: string
  roles: readonly RoleDefinition[]
  aliases?: readonly RoleAlias[]
}

interface ContributionLease {
  contributorId: string
  generation: string
  contributionDigest: string
  dispose(): void
}
```

规则：

- 唯一键是 `id@version`；version 在 v1 是不透明精确标识，不进行隐式 latest 或 SemVer 兼容解析。
- 同 ID 多版本可以共存；同一精确键重复时拒绝整份 contribution。
- alias 只能指向 canonical exact RoleRef；禁止 alias chain、循环和 alias 指向 alias。
- canonicalize 后，API 与持久化只写 canonical RoleRef。
- contribution 深克隆并冻结；旧 disposer 不能删除新 generation。
- 运行中的 Assessment/Deliberation 使用启动时冻结的 PrivateRoleSnapshot；贡献卸载只影响新任务。
- 外部贡献只能写自己命名空间；`core.*` 为内建贡献保留。
- alias key 与 canonical role 使用相同 namespace ownership；九个 `core.council.*` legacy alias 由 Role Core 的内建 `core` contribution 注册，GroupX 无权写保留 namespace。
- contributor 卸载只移除自己的 canonical roles/aliases，不级联删除其他 contribution。
- `snapshot()` 每次递归验证完整 `requiresRoleRefs` closure；依赖或 alias target 已卸载时，新 snapshot/canonicalize 必须返回 unresolved，已经冻结的内存 snapshot 可完成当前运行。
- namespace owner 的判断只按规范化 contributorId 前缀进行，不读取文件路径、包名猜测或加载顺序。

所有 digest 使用 UTF-8 编码的 RFC 8785 JSON Canonicalization Scheme 与 SHA-256，字段格式固定为 `sha256:<64 lowercase hex>`：

- `definitionDigest` 覆盖完整 `RoleDefinition`，包括 Host-private Prompt；PublicRole 只公开 digest。
- `contributionDigest` 覆盖 schemaVersion、contributorId、version、roles 与 aliases 的完整规范化值。
- 数组顺序具有语义，不排序；RoleSnapshot 会先 canonicalize、去重，再按 `id@version` 字典序形成 closure 清单。
- `snapshotDigest` 的精确 preimage 是 `{schemaVersion:1,entries:[{ref:{id,version},definitionDigest}]}`；entries 按 `id@version` 排序。`snapshotId` 等于 `role-snapshot:<64 lowercase hex>`，使用同一完整 digest，不截断。
- 同一 exact `id@version` 在重启后出现不同 `definitionDigest` 时 fail closed，禁止把内容漂移视为同一版本。
- Role Core、Identity、GroupX 至少共享三组包含 Unicode、数组顺序和 Prompt 变化的 golden vectors，证明跨仓字节一致。

RoleSnapshot 分为只存在于 Host 内存的私有值与可持久化引用：

```ts
interface PrivateRoleSnapshot {
  schemaVersion: 1
  snapshotId: string
  snapshotDigest: string
  refs: readonly RoleRef[]
  definitionDigests: readonly string[]
  definitions: readonly RoleDefinition[]
}

  schemaVersion: 1
  snapshotId: string
  snapshotDigest: string
  refs: readonly RoleRef[]
  definitionDigests: readonly string[]

  contributorId: string
  version: string
  contributionDigest: string

  contributorId?: string

```

`snapshotId` 由完整 snapshot digest 派生，不是可猜测数据库主键。运行中使用深冻结的 `PrivateRoleSnapshot`；Store、API 和审计只保存 `PersistedRoleSnapshotRef`。重启后按 exact refs 重建 dependency closure 并逐项比较 digest；缺失或漂移时返回 `ROLE_SNAPSHOT_UNRESOLVED`，对应 discussion 进入 `failed_retryable`，不得换版本或继续派发。

Role Core v1 不建中心数据库。角色真源是版本化插件/角色包；消费者各自在自己的 Store 中保存 exact RoleRef。

### 4.4 SupervisionPolicy

```ts
type Autonomy = 'off' | 'guided' | 'bounded-auto'

interface GoalSubject {
  sessionId: string
  goalId: string
}

interface SupervisionPolicyRecord {
  schemaVersion: 1
  policyId: string
  policyRevision: number
  subject: GoalSubject
  boundGoalRef: GoalRef
  status: 'observing' | 'suspended' | 'review-required' | 'closed'
  autonomy: Autonomy
  successCriteria: readonly string[]
  nonGoals: readonly string[]
  supervisorRoleRefs: readonly RoleRef[]
  stallPolicy: {
    unchangedRounds: number
    sameBlockerRounds: number
    verifierFailureRounds: number
  }
  councilPolicy: {
    enabled: boolean
    candidateSnapshot?: CandidateSnapshotRef
    maxDeliberationsPerGoal: number
    cooldownRounds: number
    maxParticipants: number
    maxCallsPerGoal: number
    maxCallsPerDeliberation: number
    maxDiscussionRounds: number
    manualTimeoutMs: number
    autoPreparationDeadlineMs: number
  }
  contextLimitChars: number
  authorizedBy: 'user-command' | 'user-client-action'
  createdAt: number
  updatedAt: number

```

该记录不保存 Goal objective、phase、roundsStarted 或 activation 的权威副本。`subject` 允许同一个 Goal 跨 phase-only revision 恢复，`boundGoalRef` 用于每次操作的精确 CAS。

Goal 变化规则固定为：

| Goal 变化 | Policy | Assessment/停滞窗口 | bounded-auto grant / 进行中 discussion |
| --- | --- | --- | --- |
| pause、block、进程重启后 activation=disarmed | `suspended`，不评估、不续行 | 历史保留，连续停滞窗口清零 | 立即撤销/取消；不得自动恢复 |
| 同 goalId 的 phase-only resume | 自动把 `boundGoalRef` rebind 到新 revision 并恢复 guided 观察 | 历史与总预算保留，连续窗口从 0 开始 | grant 不跨 revision，需用户重新授权 |
| objective、成功标准相关元数据或非 phase 语义 edit | `review-required` | 历史只读保留，窗口清零 | 撤销 grant；用户确认新 criteria 并 update/reattach 后才继续 |
| complete / clear | `closed` | 只读归档 | 取消非终态 discussion，不可重新派发 |

所有 revision 变化都递增 Coordinator generation，并使旧异步结果失效。预算账本按稳定 `GoalSubject` 累积，禁止通过 pause/resume 重置配额。restart 后只恢复持久状态，不自动 resume Goal；用户用官方 Goal API resume 后再按上表 rebind。

`councilPolicy` 是单次/自动策略上限，不是预算真源；BudgetLedger 始终取更严格值，policy update 不得创建 ledger、恢复已用量或提高 Goal 总额度。

`evidenceDigest` 来自有界证据投影；Store 不保存原始聊天、原始工具输出或私有文件路径。LLM 评估只能补充确定性信号，不能覆盖可验证的 Goal/todo/test 事实。

当 Assessment 的 action 首次变为 `recommend-council` 时，Supervisor 在同一 Store transaction 内创建一条不可变 RecommendationRecord；`recommendationId` 是 hash(assessmentId, policyRevision, generation, kind) 的稳定 ID，同一 Assessment 最多一条。`recommendedIssue` 只能由脱敏 Assessment 字段确定性生成。Decision 单独追加，Recommendation 本身不改写；`accepted-awaiting-pause` 可以跨“为执行该建议而发生的 pause/disarm”使用，但请求时仍必须匹配同一 subject、goalSemanticDigest 与 policyRevision。语义 edit、policy update/detach、complete/clear 或 restart 会使未消费建议不可执行；`declined` 只抑制同一 assessment/generation。

Policy attach 前必须有至少一条用户确认的 `successCriteria`；`nonGoals` 可为空。系统可以根据 Goal objective 生成草案，但草案在用户通过命令或 Client 明确确认前不能激活 policy。v1 的确定性评估始终启用；可选 `AssessmentEvaluator` 默认关闭，启用时必须锁定一个经配置验证的 Supervisor model route，每个最终 Goal Round 最多调用一次、15 秒、输入 12,000 字符、输出 4,000 字符，并计入独立的每 Goal 50 次默认上限。失败不在同一 Round 重试，只产生 `unknown`/degraded 信号，绝不使 Goal turn 失败。

Assessment/Artifact 要进入模型时先建立 `pending` DeliveryRecord。Driver 的 before-next-round seam 覆盖每一个 Goal queue candidate（包括初始/重启 resume 后没有 completed turn 的 candidate），把语义仍匹配的 pending delivery CAS 为 exact `bound`。Goal `user/message` 与对应 runtime-context snapshot 持久提交后变为 `admitted`；同一 Goal turn 后续 step 继续使用 turn tracker 中的冻结 section，但不会再次消费 delivery。crash 后若日志能证明 exact admitted snapshot 则恢复为 admitted；只有 bound 而未 admitted 时，同语义可退回 pending 并重新绑定，否则 invalidated。human/superseded candidate 永不消费 delivery。

| --- | --- |
| policy/candidate/grant/deliberation/reservation/member/idempotency ID | 对应命名空间的安全 ASCII 标识，1～128 字符 |
| revision / attempt / generation / round | 0～2,147,483,647 的 safe integer；需要正数的字段最小 1 |
| timestamp | 0～8,640,000,000,000,000 的 safe integer milliseconds |
| successCriteria/nonGoals | 各最多 32 项，单项 1,000 字符，合计 16 KiB；criteria 至少 1 项 |
| issue / recommendation | 各最多 4,000 字符 |
| evidenceSummary / rationale / dissent / evidenceGaps / planChanges | 各最多 32 项、单项 1,000 字符；单 Artifact 总文本 32 KiB |
| candidate/execution actors | 协议最多 8，默认最多 4；按 distinct ActorRef 计数，memberRef 单项最多 128 字符 |
| candidate/plan RoleBindings | 最多 16；同一 Actor 可占多个不同 slot/RoleRef，tuple 不得重复 |
| requiredRoleRefs | 最多 16；重复 ref 拒绝 |
| maxDeliberationsPerGoal | 1～8，默认 2 |
| maxCallsPerGoal | 1～128，默认 12 |
| maxCallsPerDeliberation | 1～64，默认 8，且不得超过 Goal 剩余容量 |
| maxDiscussionRounds | 1～4，默认 2 |
| timeoutMs | 手动 1,000～300,000，默认 120,000；自动 1,000～45,000，默认 45,000 |
| contextLimitChars | 256～16,000，默认 4,000 |

人类文本先做 Unicode NFC，允许换行/tab，拒绝其他 C0/C1 控制字符、NUL、非字符串 getter/prototype pollution 和数值 overflow。越界统一返回 `SUPERVISION_PROTOCOL_INVALID` 或 `SUPERVISION_LIMIT_EXCEEDED`，不得截断后悄悄接受；只有 evidence projection 的内部安全摘要允许按明确算法截断并记录 `truncated=true`。

Candidate snapshot 由 GroupX 在用户从其公开成员目录选择 `memberRefs` 后持久签发，表示用户批准的候选池而非实际执行名单；memberRef 不是自由 provider/model ref。相同 selectionId 的 roster/RoleBinding 变化必须 CAS 增加 revision，并立即把旧 revision 标记 superseded，不等 TTL；`validateCandidateSnapshot()` 只接受 current revision、完整 digest 和未过期 ref。`candidateActorCount` 与 `maxParticipants` 均按 distinct ActorRef 计数；同一 Actor 的多角色是多条 binding，不会被误算成多人。Client 只接收 PublicCandidateSnapshotDTO，不接收 provider/model/credential。默认 TTL 24 小时、协议最大 7 天。Grant 同时绑定 exact GoalRef、policyRevision、candidate snapshot 与可用的 contextCapabilityRevision，默认 TTL 24 小时且不得晚于 candidate expiry；任一变化、用户撤销、过期、pause/block/restart 都使其失效。

每次 dispatch 前必须先由 metadata-only、无模型调用的 `planParticipants()` 冻结 exact execution roster。ParticipantPlan 只能从 current candidate 的完整 RoleBindings 取子集，distinct Actor 数为 1～maxParticipants，必须覆盖 requiredRoleRefs，不能新增/替换 Actor、slot、RoleRef 或模型；同一 idempotencyKey+attempt 的重复 plan 必须返回同一 planDigest。Supervisor 独立重验后把 plan 与 Deliberation、BudgetReservation 原子持久化。Plan 创建不消耗 Council calls，Provider 若无法在不执行模型的情况下规划则 v1 fail closed。candidate/role snapshot/generation 在 plan 后、dispatch 前变化时释放 reservation 并拒绝；receipt 与 result 都必须回显 exact planDigest，任何减少、扩充或替换都按 `SUPERVISION_PARTICIPANT_PLAN_MISMATCH` 失败并保守结算，不把结果交付 Goal。

默认 Goal ledger 为 2 次 discussion、12 次 calls；单次 discussion 默认最多 8 calls，且请求上限必须小于等于 `min(8, remainingCalls)`。Ledger 不保存可漂移的聚合计数，而从 reservations 确定性计算容量：`reserved → (1,reservedCalls)`、`accepted → (1,reservedCalls)`、`settled → (chargedDeliberations,chargedCalls)`、`released → (0,0)`；同一 reservation 在任一时刻只采用一行贡献，绝不把 charged 与 reserved 再相加。`remaining = limit - Σ(reservation contribution)`，discussion/calls 分别计算。Policy/grant 更新不能降低到已 committed 以下；提高 Goal 总额度只能由用户单独确认 budget amendment 并审计，不能通过 pause/resume 或普通 policy update 重置历史。

首次满足 Goal/policy/candidate/状态准入的 manual 或 bounded-auto 请求，在“创建第一条 reservation”的同一 CAS transaction 内 `ensureGoalLedger()`：缺失时以 revision=1 和 `min(部署默认值, current policy per-goal limits)` 建立，随后立即预留；竞争创建者只能有一个成功。普通 policy/grant update 不能走此入口。显式 budget amendment 可用 expectedLedgerRevision=0 预建 ledger，已有 ledger 则必须 exact CAS，且不得低于 reservations 推导出的 committed 容量。

结算规则固定为：请求创建时状态 `reserved`，charged 均为 0；`dispatch()` 返回持久 receipt 后原子转 `accepted`，设置 receiptDigest/acceptedAt、chargedDeliberations=1、chargedCalls=0，但在 usage 未知前整笔仍按 `(1,reservedCalls)` 占容量。receipt 前取消/失败转 `released`；receipt 后取得结果/取消/timeout/部分失败时转 `settled`，按可证明 actualCalls 写 chargedCalls，无法证明时 chargedCalls=reservedCalls。usage 可证明时必须满足 `0 ≤ chargedCalls = actualCalls ≤ receipt.callCeiling ≤ reservedCalls` 以及 `discussionRounds ≤ maxDiscussionRounds`；无法证明 actualCalls 时省略 actualCalls 并全额结算，越界 Provider 结果也按协议错误全额结算。每条 reservation 持久保存 receipt/usage digest 与 acceptedAt/settledAt，重启可重放。若 Provider 已接受而 Host 在 receipt 落盘前 crash，reconcile 必须凭相同 idempotencyKey/attempt 找回同一 receipt，再从 reserved CAS 到 accepted，不得释放后重派。相同 key 的 status/reconcile 不重复计费；用户对 `failed_retryable` 发起新 attempt 必须使用新 key 并重新预留。没有可用的下一 Goal Round capacity 时，不允许 bounded-auto 消费预算，只持久化建议并提示用户处理 round cap。

Reservation 字段组合也必须 fail closed：reserved=`(chargedDeliberations=0,chargedCalls=0,no receipt)`；accepted=`(1,0,receipt+acceptedAt)`；settled=`(1,0..reservedCalls,receipt+acceptedAt+settledAt)`；released=`(0,0,no receipt,settledAt)`。Store load/reconcile 每次重算这些 invariant 和 Ledger 剩余量，非法组合不被自动“修正”。

### 4.8 Supervisor/Council digest 规则

领域 digest 同样使用 RFC 8785 canonical JSON + SHA-256，digest 字段本身不参与计算：

- `evidenceDigest` 覆盖按稳定 source/subjectRef 排序的脱敏 evidence DTO，不含 wall-clock timestamp。
- `artifactDigest` 覆盖 DecisionArtifact 除 artifactDigest 外的完整字段，数组顺序具有语义。
- `goalSemanticDigest` 覆盖 `{goalId,objective}`，排除 phase/activation/revision；`policySemanticDigest` 覆盖 successCriteria、nonGoals、RoleRefs、stall/council policy，排除 ID/revision/timestamp。
- `rosterDigest` 由 GroupX 对其冻结的完整 candidate roster 计算；Supervisor 只持有安全 ref/digest，Provider 验证时必须逐字节重算匹配。
- `planDigest` 的精确 preimage 是 `{schemaVersion,deliberationId,attempt,candidateSnapshot,roleSnapshot,requiredRoleRefs,maxParticipants,participantActorCount,participantBindings}`；不含 planId/planDigest/createdAt，数组顺序具有语义。`planId` 等于 `participant-plan:<64 lowercase hex>`，receipt/result 必须回显完整 digest。
- correlation/idempotency key 对架构列出的稳定字段做 canonical hash；不得拼接 Prompt、原始消息或凭据。
- 所有对外显示使用短前缀，CAS/重放比较始终使用完整 32-byte digest。

## 5. CouncilService 合同

GroupX 作为可选 provider，实现一个 Host 内窄接口。Supervisor 不通过浏览器 HTTP 拼接 GroupX 内部状态，也不切换用户的 Group 模式。

```ts
interface CouncilRequest {
  schemaVersion: 1
  deliberationId: string
  idempotencyKey: string
  attempt: number
  mode: 'advisory'
  goalRef: GoalRef
  issue: string
  evidenceSummary: readonly string[]
  roleSnapshot: PrivateRoleSnapshot
  participantPlan: PersistedParticipantPlan
  budget: CouncilBudget
}

interface PublicCouncilStatus {
  deliberationId: string
  attempt: number
  status: DeliberationStatus
  updatedAt: number
  actualCalls?: number
  dispatchReceipt?: CouncilDispatchReceipt
  stableStopReason?: CouncilStopReason
}

interface CouncilService {
  issueCandidateSnapshot(
    request: CandidateSelectionRequest,
    signal: AbortSignal,
  ): Promise<ValidatedCandidateSnapshot>
  validateCandidateSnapshot(ref: CandidateSnapshotRef): Promise<ValidatedCandidateSnapshot>
  planParticipants(request: ParticipantPlanRequest, signal: AbortSignal): Promise<PersistedParticipantPlan>
  dispatch(request: CouncilRequest, signal: AbortSignal): Promise<CouncilDispatchReceipt>
  result(deliberationId: string, attempt: number, signal: AbortSignal): Promise<CouncilResult>
  cancel(deliberationId: string, attempt: number): Promise<void>
  status(deliberationId: string, attempt: number): Promise<PublicCouncilStatus | undefined>
}
```

约束：

- candidateSnapshot 必须由明确用户动作调用 `issueCandidateSnapshot()`，memberRefs 只能来自 GroupX 的有界公开目录；Provider 持久保存 selection lineage/current revision。Supervisor 独立校验 `planParticipants()` 的 exact subset/required roles/count/digest，并在任何预算预留或 dispatch 前把 PersistedParticipantPlan 冻结进 DeliberationRecord。
- GroupX 在 current revision 提交后发出安全 `council/candidate-changed {selectionId,revision,snapshotId}`；Supervisor 立即递增 generation/撤销旧 grant。事件丢失或重启时，dispatch 前 mandatory validate 仍 fail closed。
- Supervisor 只能请求 RoleRef 和能力缺口，不能传自由 provider/model 让 GroupX 自动扩员。
- Council v1 的能力 envelope 固定为 `llm-only/advice-only`。
- CouncilService 缺失、超时或失败时，Supervisor 返回降级 Assessment，stock Goal 继续。
- GroupX 负责参与者执行、观点收集与合成；Supervisor 负责是否请求、预算授权和结果是否仍匹配 current GoalRef。
- `CouncilRequest`、Candidate/Receipt/Result DTO 是 JSON-only 业务 DTO；`AbortSignal` 是同进程生命周期控制参数的唯一例外，不持久化、不进入 HTTP。未来跨进程 Provider 必须改用 opaque cancellation token。
- `dispatch()` 只能执行 Request 中的 exact ParticipantPlan；返回 receipt 前没有 Provider 接受事实，返回后 Supervisor 原子持久化 receipt 并把 reservation 转 accepted。`result()` 与 `status()` 必须复用同一 providerOperationId/attempt/participantPlanDigest，不能隐式开启新运行或替换名单。
- v1 不存在 formal ratification；GroupX 可以在最多 `maxDiscussionRounds` 内并行收集观点并合成一次 advice-only Artifact，但不得把内部多数意见标为用户批准或系统共识。

Host transaction 顺序固定为：① 验证 manual/bounded trigger、Goal/policy/generation 与 current candidate；② 从 Role Core 构建 PrivateRoleSnapshot；③ metadata-only plan 并独立验证 exact subset；④ 再次验证 candidate/role snapshot/Goal/generation；⑤ 在一个 Store CAS 中 ensure ledger、写 Deliberation(requested+plan) 与 BudgetReservation(reserved)；⑥ immediately pre-dispatch 再做 mandatory candidate/role/Goal/generation validate，陈旧则 CAS released；⑦ dispatch exact plan；⑧ 按 receipt/usage 状态机结算。任何实现不得在 plan 冻结前预留预算，也不得在 reservation 持久化前 dispatch。结果中的 planDigest 不匹配时保留安全错误与 usage 证据、保守结算，但不创建 DeliveryRecord。

## 6. Goal 共存与模型上下文

### 6.0 Goal 读取真源

Supervisor 的 `native-goal` adapter 对 exact live Agent 必须调用 `ctx.goals.get(agent)` 获取 current GoalView、activation 与实时 roundsStarted；持久 Goal projection 只作为非 live session 的 durable fallback。projection 不拥有 activation，连续 Round 中的 roundsStarted 也可能滞后，因此非 live session 的 activation 必须返回 `unknown`，Client/API 不得猜测。

### 6.1 最小 upstream policy seam

现有 `agent/turn-stopping` 是可被其他 Stop hook `steer()` 后重复进入的候选停止点，不具备 Goal turn finality。它最多用于无副作用的 provisional evidence watermark；不得在该事件持久化最终 Assessment、预留预算或派发 Council。

P4 在原生 Goal 包新增：

```ts
'goal/before-next-round'(
  this: Scoped<Agent>,
  payload: {
    agent: Agent
    input: {
      sessionId: SessionId
      goalRef: GoalRef
      objective: string
      completed?: {
        round: number
        goalMessageId: MessageId
        turn: number
        admittedSeq: number
        turnEndSeq: number
        reason: TurnEndReason
      }
      candidate: {
        round: number
        maxGoalRounds: number
      }
      correlationKey: string
      deadlineAt: number
    }
    signal: AbortSignal
  },
): Promise<void> | void
```

`input` 是冻结、JSON-compatible DTO；`agent` 只是 DSH scoped subject，不能进入 Supervisor/Council DTO、Store 或日志。事件没有返回值、没有 veto、没有 Goal mutation 权；Driver 仍是唯一创建 reservation、render 固定 prompt 和调用 `followup()` 的组件。

Driver 扩展自己的 RoundAttempt：在 `agent/inbox/claimed` 记录 Goal turn，在匹配 admitted `user/message` 时记录 admittedSeq，只在匹配 `turn/end` 后形成 pendingCompletion。before-next-round 覆盖每一个 queue candidate；初始创建、重启或 resume 后没有已完成 Goal turn时 `completed` 为空，只允许绑定 pending Delivery，不执行 Assessment/自动 Council。事件插入顺序固定为：

1. 完成现有 Session durability checkpoint；
2. 读取并校验 exact live Goal、active/armed 与下一 Round capacity；
3. 先取得固定 listener snapshot；若为 0，字节级沿用现有 stock render/reservation/followup 路径，不进入 maintenance；
4. 有 listener 时才进入 Driver 自己的 `agent.runMaintenance()`，在 render prompt、reservation 和 followup 之前执行 awaited parallel-settled seam；
5. maintenance acquisition 与其他维护冲突时视为 transient，`whenIdle()` 后合并重试，不进入通用错误/disarm 路径；
6. listener reject/普通 timeout 只记录安全诊断并 fail-open；
7. listener snapshot 非空时，先决定 `handled | superseded-consumed`，append internal checkpoint，并在剩余 deadline 内显式 `await ctx.sessions.flush()`；
8. flush 后再次重检 competing input、Goal/capacity、preparation token 和新 checkpoint，仅由 Driver 决定是否按 stock 行为 queue。

当 listener snapshot 非空时，Driver 额外写入不对模型可见的 session internal `goal/policy-seam-checkpoint`，只含 stable correlationKey、completed messageId/turn/turnEndSeq 和 `handled | superseded-consumed` disposition。append 只算内存发布，不能作为 durability 证据；必须在任何 Goal reservation/followup 或释放 human wake latch 前显式 await `ctx.sessions.flush()`。flush 成功后若二次重检发现 flush 期间出现 competing human/Goal change/capacity change/较新 checkpoint，则不得 queue，并追加、再次 flush 同 correlation 的 `superseded-consumed`（后写 disposition 胜出）。

checkpoint flush reject/超时属于 fail-local durability fault：绝不进入 Goal 的通用 error/disarm，也不阻塞已在等待的人类输入；本次不得把“append 成功”当作 durable handled。若仍满足 stock queue 条件，Driver 可在最终 reservation fence 后 fail-open queue，重启时由稳定 correlation + Supervisor/Provider CAS 幂等重放；若已 superseded，则保持 Goal reservation 为 0，恢复时把 durable 的后继 ordinary/human user-message/turn boundary 也视为 superseding 证据。没有 durable checkpoint 或后继 superseding boundary 时允许同 correlation 重试，但禁止重复 Assessment、预算或 Provider side effect。启动时由 durable Goal user/message、turn/end、ordinary/human boundary 与 checkpoint 重建 pendingCompletion。零 listener 不 append/flush 此事件，stock transcript/event path 不变。

最终重检至少包括：Host/fiber/Agent 仍 live、preparation token 最新、无 competing nextTurn/已有 reservation/新 checkpoint、Goal id+revision+phase+activation 未变、candidate round 未超 cap；若 completed 存在，再检查 roundsStarted、pendingCompletion messageId/turn/turnEndSeq。signal 未因 supersede 取消，原 pre-step 双重 reservation fence 不得删除。

在 maintenance 期间插入任何非 Driver 自身的 nextTurn 时，Driver 只 abort 自己的 preparation controller，绝不调用 `agent.cancel()` 或清空 inbox；Goal reservation 为 0，maintenance 退出后由既有 wake latch 优先运行人类输入。该 pendingCompletion 原子标记 `superseded-consumed`，同 correlation 不再 Assessment/Council；human turn 后下一次 stock Goal queue 使用 `completed=undefined`，只允许重新绑定仍有效的 pending Delivery。Goal change、pause、clear、agent dispose 或插件 unload也属于 superseded，不走 fail-open queue。超时后仍运行的旧任务必须由 correlationKey + generation + CAS 阻止迟到提交。

guided 模式只在 seam 内持久化 `recommend-council/await-user` 并立即返回，不隐式暂停 Goal。bounded-auto 才允许在 45 秒自动 preparation deadline 内 await Council；超时 fail-open。若产品未来需要 guided 阻止下一 Round，用户必须显式调用原生 Goal pause，或另立 durable deferral ADR，不能让 policy listener 偷偷 veto Driver。

若 `roundsStarted >= maxGoalRounds`，Driver 按 stock 规则 block 且不触发 before-next-round；Supervisor 只能从 durable Goal/turn 事件生成 fail-local 的 terminal `round-cap-reached` UI/审计状态，不启动 Council、不生成无法被消费的 deliverTo。

### 6.2 动态上下文

Supervisor Host fiber 全局注册一次 provider，并通过 `AssembleContext.agent` 查询 exact per-agent deliverable：

```ts
ctx.systemPrompt.context({
  name: 'supervisor:assessment',
  order: SUPERVISOR_CONTEXT_ORDER,
  text: assembleContext => safelyRenderExactGoalContext(assembleContext.agent),
})
```

text provider 必须同步、total，并在内部 catch 后返回空字符串；任何 Store/解析错误都不得使 pre-step 抛错或 Goal disarm。Turn tracker 在首个 `next-turn` claim 记录 `{exact Agent,turn,GoalMessageSource}`，直到匹配 `turn/end` 才清除；该 Goal turn 因 steer 产生的所有 `next-step` pre-step 都可渲染同一冻结 section。human、ordinary、subagent、下一 turn 或 stale Agent 一律返回空。

DSH 通过 RuntimeContextProjection 产生带来源的 durable user-message snapshot。验收按 snapshot 中 `sections[name='supervisor:assessment']` 的最新有效 section/digest 判断；其他动态 context 变化可能产生 superseding snapshot，不能断言原始 transcript 中该文本只出现一次。clear 也只会在下一次 pre-step 形成清除 snapshot。

P4 同时修正 Goal Driver 对尚未 admitted runtime-context snapshot 的恢复规则：Goal reservation 在 pre-step 失效时，`@deepseek-ai/dsh-system-prompt` 的 snapshot 标记为 non-restorable，或由 `restoreOtherClaimed()` 明确丢弃并在下一次 assemble 重算，禁止把 Goal 专属 context 恢复到 human turn。

上下文只包含：

- GoalRef/round 的显示性短标识；
- 已满足和缺失的成功标准；
- 可解释进展/停滞信号；
- 最新有效 Decision Artifact 摘要；
- 分歧、证据缺口和建议计划修订；
- 明确提示“这是监督建议，不是已执行事实”。

P4 同步为 SystemPrompt Service 增加只读 `runtimeContextCapability(agent): {available:boolean; revision:number; reason?:string}` 与 scoped capability-changed 通知，封装 private include/suppress layers。unknown 默认 unavailable；Supervisor 在预算预留/dispatch 前读取 exact capability revision，变化会 abort preparation 并递增 generation。Profile 的 `includeRuntimeContext=false` 或 agent scope suppression 会进入 `SUPERVISION_CONTEXT_UNAVAILABLE`：Assessment 可用于 UI/审计，但 bounded-auto 不派发 Council。complete/clear、policy detach 或 deliverTo 失效时 provider 返回空；旧 section 在下一 pre-step 被 superseding/clear snapshot 取代。

### 6.3 为什么只扩展而不替换 Driver

stock Driver 已负责 durability checkpoint、reservation、竞争消息、人类输入优先、取消、disarm、pre-step 前后校验和 unload drain。现有事件没有同时满足“Goal turn final、可 await、下一 reservation 前、可取消、失败不影响 stock Goal”的接缝，因此新增一个最小 policy event 和 non-restorable runtime-context 修正；不 fork Driver、不改固定 `<goal_round>` renderer、不把调度权交给 Supervisor。

## 7. 数据流

### 7.1 创建并附着监管

```text
用户 → 官方 Goal API goal.create
     → goal/change 持久提交 + Goal projection 更新
用户 → Supervisor API attach-policy(goalRef, settings)
     → CAS 校验 current GoalRef
     → SmartSupervisionStore 原子写入
     → Client 显示 Goal + Policy 两个独立状态
```

Goal 创建成功但 policy attach 失败时保留 Goal，显示“Goal 正常运行、智能监管未附着”，允许重试；禁止删除或回滚 Goal。

### 7.2 正常 Goal Round

```text
stock Driver queue GoalMessageSource
  → pre-step 组装上一次有效 supervisor runtime-context
  → Agent 执行工具/回复
  → 最终 turn/end + durability checkpoint
  → Driver 在 before-next-round maintenance 触发 policy seam
  → Supervisor 读取有界证据并计算一次最终 Assessment
  → progress=advanced，持久化 Assessment
  → listener 返回，Driver 重检并独立决定下一 Round
```

### 7.3 停滞与讨论

```text
goal/before-next-round
  → deterministic stall detector
  ├→ guided：原子写 RecommendationRecord 后返回；accept 本身不派发
  └→ bounded-auto：校验 grant、冷却、Goal round/context capacity
       → validate current CandidateSnapshot + rebuild PrivateRoleSnapshot
       → metadata-only planParticipants；冻结并重验 exact ParticipantPlan
       → 原子 ensure BudgetLedger + DeliberationRecord + reserved reservation
       → immediately pre-dispatch revalidate
       → CouncilService.dispatch(exact plan, signal) → persist receipt + accepted
  → CouncilService.result(signal) → settle usage
  → 校验 planDigest + GoalRef + generation 未变化
  → persist DecisionArtifact / unresolved / stable failure
  → listener 返回
  → Driver 最终重检后 queue；目标 Goal Round 获得有界 runtime-context
```

### 7.4 人类竞争输入

Assessment/Council 运行于 Driver 的 awaited before-next-round maintenance 并使用 preparation signal。人类消息进入 inbox 时 Driver abort preparation 且不创建 reservation；Supervisor 不消费该消息。监听返回后由既有 wake latch 先运行人类输入。Supervisor 提交前再次校验 GoalRef、round、generation、correlationKey 和 cancellation，旧结果只保留安全审计或被丢弃。

## 8. 状态机

### 8.1 原生 Goal

保持原状态：

```text
active(armed/disarmed) ↔ paused
active/paused/blocked → complete/clear 等原生转换
```

Supervisor 不添加新 Goal phase。

### 8.2 SupervisionPolicy 运行状态

```text
detached
   ↓ attach exact GoalRef
observing
   ↓ matching final Goal completion / before-next-round
assessing ──progress──→ observing
   ├─needs user──────→ awaiting-user ──confirm/decline──→ observing
   ├─authorized stall→ deliberating ──result/degrade──→ observing
   └─local failure───→ degraded ──next valid round/retry──→ observing

pause / block / restart-disarmed → suspended ──phase-only resume──→ observing
semantic edit → review-required ──user confirms criteria/update──→ observing
complete / clear / detach → closed
unload → runtime disposed；持久 policy 下次加载为 suspended
```

`assessing/awaiting-user/deliberating/degraded` 是运行时事务状态，不是持久 Policy status 或 Goal phase。只有一个 session+generation 可以进入这些状态。

### 8.3 Deliberation

```text
requested → dispatching → collecting → synthesizing
                                      ├→ resolved
                                      └→ unresolved
任意非终态 ├→ failed_retryable
           ├→ timed_out
           └→ cancelled
failed_retryable ──user retry creates new record/attempt/key/reservation──→ requested
```

重启遇到非终态时进入 reconcile：若 provider 不能证明同一 idempotencyKey 的状态，则转 `failed_retryable`，不得猜测 resolved 或重复计费。

## 9. 并发与幂等

每个 session 维护一个进程内 Coordinator：

- `generation` 在 Goal revision、policy revision、user detach、agent resume/dispose 时递增；
- 任意 competing human/ordinary nextTurn 会 abort 当前 preparation；其结果不得成为该 human turn 的 context；
- 同一时间只有一个 assessment task；
- Driver stable correlationKey = hash(sessionId, goalRef, optional completed messageId/turn/turnEndSeq, candidate round)；进程内 preparation token 只用于 stale 重检，不进入 key。只有 completed 存在时创建 Assessment，重复 provisional stopping/crash retry 不产生第二次最终评估；
- bounded-auto Deliberation key = hash(driver correlationKey, policyRevision, grantId/revision, candidate snapshot, attempt)；manual key = hash(subject, goalSemanticDigest, policyRevision, candidate snapshot, manualRequestId, attempt)。bounded-auto trigger 与 manual discriminated trigger 都持久保存完整安全 preimage；
- 调用前原子预留预算；失败后按协议结算，不允许并发超支；
- 异步任务提交前校验 exact Agent、GoalRef、completed/candidate round、policy/grant revision、generation、correlationKey 和 signal；
- 旧 generation 不得覆盖新状态或注册新 runtime-context；
- Cordis fiber 卸载先关闭新准入，再 abort 任务、等待 settle、释放 context/listener/timer。
- Service 注册 token 保证同 Host 单实例；重复 Loader row、旧 HMR fiber 或第二 Store writer 无权进入 Coordinator。

非 Goal advice/takeover 也必须通过同一 Coordinator gate。active Goal 分支永远禁止 Supervisor followup；无 active Goal 时才能走 legacy 续行路径。

## 12. Host API

### 12.1 Role Core 只读 API

- `GET /_dsh/role-core/v1/roles`
- `GET /_dsh/role-core/v1/contributors`

不提供 Prompt endpoint，不提供中心 binding 写 API。两条 GET 只接受实际 socket remote address 为 IPv4 loopback、IPv4-mapped loopback 或 `::1` 的请求；不信任 `Host`/`X-Forwarded-For` 推断来源。响应 `Cache-Control: no-store`，拒绝未知查询字段，单页最多 200 roles、64 contributors，并使用与 Supervisor 相同的安全错误体。浏览器请求有 Origin 时必须 exact same-origin；无 Origin 的本机 CLI 只允许只读 GET。

所有请求都按实际 socket remote address 验证 IPv4 loopback、IPv4-mapped loopback 或 `::1`，不信任转发头。浏览器 mutation 必须 exact same-origin；无 Origin 的 mutation 仅接受 bootstrap 签发、绑定当前 Host 进程且短期有效的 `X-DSH-CSRF` token，本机命令优先直接调用 Host Service。写 API 还要求 `application/json`、64 KiB body、合法 session id、expectedRevision、idempotency key，禁用 CORS，并返回 `Cache-Control: no-store`。

## 13. Client 架构

使用 additive composer/dock Slot，不恢复遮挡式全局浮窗。Client 拆为：

- GoalSummary：消费 Host `NativeGoalStatusDTO`；live Agent 显示精确 activation/round，非 live fallback 明示 activation unknown；
- SupervisionPolicyControls：off/guided/bounded-auto、阈值与预算；
- ProgressEvidence：显示安全信号和未知状态；
- CouncilRecommendation：成员角色、预计预算、确认/取消；
- DeliberationStatus：阶段、耗时、分歧、证据缺口和停止原因；
- RoleBindingView：明确分开展示“角色定义”和“实际模型/Agent 成员”；
- ManagedSessionsView：保留旧 Supervisor 托管会话清单，但名称和 DTO 明确区别于 GroupX participant；
- ErrorBoundary：每个可选 surface 局部失败；
- API client：generation/AbortController，旧响应不覆盖新状态。

矩阵只消费 `/states` 摘要，保持固定几何、快照排序和滚动位置。

## 16. 依赖方向

```text
deepseek-harness stock services
           ↑
dsh-role-core ← dsh-identity-library role contributor
      ↑                 ↑
      ├──── dsh-groupx CouncilService
      │            ↑
      └──── dsh-supervisor ─── official Goal services
                         ↑
                     Client APIs
```

- `dsh-role-core` 不依赖 Supervisor、GroupX、Identity、HARVIS 或 Zhitro。
- `dsh-groupx` 不依赖 Supervisor；只消费 Role Core 并提供 CouncilService。
- `dsh-supervisor` 可选消费 CouncilService；GroupX 缺席时仍能启动。
- Client 不 import Host 领域对象。
- 不允许模块级 registry singleton；Service 实例归 Host Cordis fiber。
- Supervisor 将 Role Core 与 GroupX 声明为 optional peer，只做 type-only 包 import；运行时通过固定 Cordis Service 名 `dsh.roleCore.v1`、`dsh.council.v1` 探测/inject。缺 Service 时 legacy off/advice/takeover 仍启动，smart policy 显示 typed degraded 状态；不得因静态 runtime import 在 Loader 阶段崩溃。
- GroupX 对 Role Core 采用相同 optional-service 规则：旧模式可启动，版本化 Council 能力局部禁用。Profile 决定唯一 Provider，不允许 Supervisor 扫描模块或自动选择替代实现。

## 18. 扩展点

- 新 Role contributor：注册 namespaced exact RoleDefinition，随 fiber dispose。
- 新 Council Provider：实现相同 Host Service；选择权由 Profile 组合拥有，Supervisor 不自动挑 provider。
- 新 evidence provider：只贡献有界、可哈希的事实 DTO，不返回 raw Session/Context。
- 新 stall rule：纯函数，输入 Assessment history 与 config，输出 stable signal。
- 新 Client surface：消费相同 v2 DTO，不复制业务公式。
- 未来 distributed council：另立协议和持久队列 ADR，不复用 ActorRef 冒充远程安全身份。

## 19. ADR 简表

| ADR | 决策 | 取舍 |
| --- | --- | --- |
| 001 | 原生 Goal 唯一权威 | 少一套自定义状态，但需围绕官方 GoalRef 设计 |
| 002 | 中立 Role Core | 增加一个小包，换取三方无环依赖与单一角色真源 |
| 003 | RoleRef 共享、Actor 隔离 | 绑定稍多，但避免状态和权限污染 |
| 004 | guided + bounded-auto | UI/审计更复杂，但保留用户控制 |
| 005 | GroupX 可选 Council Provider | 缺席时能力降级，但 Host 启动可靠 |
| 006 | 每 queue candidate 的最小 seam + capability + DeliveryRecord | 需要小型 upstream 改动；换取 finality、resume 首轮、用户优先和 exact context |
| 007 | side-by-side Store | 暂时存在两个文件，换取零破坏回滚 |
| 008 | Host 权威、Client DTO | RPC 代码更多，但刷新和并发一致 |
| 009 | Decision Artifact 代替 transcript | 丢失部分细节，但显著降低隐私/token/注入风险 |
| 010 | P0 先恢复工程真源 | 延后功能开发，但后续可审查、可发布、可回滚 |
| 011 | stable GoalSubject + exact bound GoalRef | phase-only resume 可恢复；grant 不跨 revision，语义 edit 需复核 |
| 012 | Council v1 仅 advisory | 不提供 formal ratification，避免把多数意见伪装成批准/共识 |
| 013 | 单 Host writer、拒绝第二实例 | v1 不支持分布式 writer，换取 Store/调度确定性 |
| 014 | Candidate pool 与 exact ParticipantPlan 分离 | 多一步 metadata plan，换取实际执行名单可冻结、可重放、不可临场替换 |
| 015 | reservation 状态推导 Goal budget | 多一个 accepted 中间态，换取 receipt/usage crash window 的容量守恒与幂等结算 |
