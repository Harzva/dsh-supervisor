# DSH Smart Supervision v2 需求分析

> 状态：需求与产品决策基线已批准（2026-08-27）；P0 已于 2026-08-28 按单独授权完成闭环，P1/P2 仍冻结。

## 1. 项目目标

把 `dsh-supervisor` 从“todo/最近对话驱动的短建议与自动 followup”升级为 DSH 的智能监督控制面：它理解并监督原生 Goal，持续判断目标是否取得可验证进展，在必要时提出重规划或召集有界多角色讨论，并把经过裁决的结论安全地提供给下一 Goal Round。

完成后的系统必须满足三个原则：

1. **一个目标真源**：Goal 的 objective、phase、revision、round 与 activation 只由 DSH 原生 Goal 领域拥有。
2. **一个续行调度器**：active Goal 的下一轮只由原生 Goal Round Driver 排队，Supervisor 不再并行注入续行消息。
3. **共享角色、隔离成员**：学院 Supervisor 与 Group 参与者引用同一版本化角色定义，但不共享成员实例、会话、模型故障或执行权限。

## 2. 用户与系统角色

| 角色 | 责任 |
| --- | --- |
| 用户/产品负责人 | 创建或编辑 Goal、选择监管自治级别、批准角色与预算、验收最终结果 |
| DSH Goal 领域 | 持久化 Goal 生命周期、CAS revision 与 Round；live Agent 进程内拥有 activation |
| Goal Round Driver | 唯一负责 active Goal 的下一 Round 准入和排队 |
| Supervisor | 读取证据、评估进展、发现停滞、生成监督上下文、请求讨论和记录审计 |
| Role Core | 提供版本化角色定义、精确解析、Prompt 保密和贡献生命周期 |
| GroupX/Council Provider | 使用人工批准的候选成员执行有界讨论并返回 Decision Artifact |
| Client/会话矩阵 | 展示权威状态并发送明确用户操作，不持有业务真源 |
| 运维/开发者 | 管理版本矩阵、Profile 组合、回滚、秘密扫描与运行时验收 |

## 3. 名词定义

- **Goal**：DSH 原生同会话持久目标，不等于 todo，不等于 Supervisor 计划。
- **SupervisionPolicy**：以稳定 `(sessionId, goalId)` 为 subject、用 exact bound GoalRef 做 CAS 的成功标准、自治级别、停滞规则、讨论预算与角色策略；不复制 Goal phase。
- **Assessment**：针对一个 Goal Round 之后的结构化进展判断。
- **Recommendation**：由 Assessment 确定性派生、不可变且可接受/拒绝的讨论建议；接受本身不派发。
- **Stall**：由可重复、可解释的信号确认的停滞，不等于任务困难或模型不确定。
- **Deliberation**：一次可取消、有预算、有截止时间且幂等的多角色讨论事务。
- **CandidateSnapshot**：用户从 GroupX 公开目录批准的候选 Actor/RoleBinding 池，不等于实际参会名单。
- **ParticipantPlan**：在 dispatch 前从 current CandidateSnapshot 冻结的 exact execution Actor/RoleBinding 子集，receipt/result 必须绑定其 digest。
- **Decision Artifact**：讨论的有界结果，包含建议、依据、分歧、证据缺口、建议计划修订和停止原因，不包含原始完整对话。
- **RoleDefinition**：版本化角色语义与内部 Prompt 合同。
- **ActorRef**：模型、Agent 或 Harness 等实际执行载体的无凭据引用。
- **RoleBinding**：在特定 slot 中把 ActorRef 绑定到一个精确 RoleRef；多角色用多条 binding 表示。
- **学院/SupervisorProfile**：长期监督职责配置，引用 RoleRef 和监督策略。
- **Group 成员**：某次 Deliberation 的 ParticipantPlan 中实际执行 Actor/RoleBinding，生命周期只属于该次运行。

## 4. 当前问题

### 4.1 Goal 与监管冲突

当前 Supervisor 只把 active Goal 当作“应让位”的条件，却没有完整覆盖 watchdog 调度路径。结果是原生 Goal Round 与 Supervisor followup 可能同时竞争同一会话。

### 4.2 计划并不智能

当前 `plan` 主要依赖 todo 和短对话窗口，只输出一句下一步建议。它缺少成功标准、进展证据、停滞判断、计划修订、成本预算、失败归因和目标级审计。

### 4.3 角色模型重复

`faculties`、`mentors`、Identity 和 GroupX 角色/成员分别定义 Prompt、标签与路由，既不能精确版本解析，也无法证明两个界面显示的是同一角色语义。

### 4.4 学院圆桌不是真正按需协作

配置 faculties 后，当前实现每次建议都调用全部学院并裁决；它没有困难检测、候选冻结、角色补齐、预算、讨论事务或持久恢复。

### 4.5 文档与源码漂移

当前上下文文档声明了结构化上下文、历史建议和 context summary，但源码仍主要读取有限的 surface 尾部。包版本、源码注释和行为说明也不一致。

### 4.6 缺少可恢复开发真源

Supervisor 当前目录没有 Git 元数据和规范 `src` 源码面。直接继续改 `lib` 会使构建、审查、制品和回滚无法可靠闭环。

## 5. 做与不做

### 5.1 本项目要做

- 与 DSH 原生 Goal 和 Goal Round Driver 正式组合。
- 为 stock Goal Driver 增加最小、fail-local 的 awaited `goal/before-next-round` policy seam；只在最终提交的 Goal turn 与下一 Round reservation 之间完成监督评估/可选有界讨论。
- 通过带 exact `deliverTo` 的 `systemPrompt.context()` 只把有界结果交给目标 Goal Round；不得泄漏到 human/ordinary turn。
- 建立中立、版本化、Prompt 不出 Host 的 Role Core。
- 将 legacy mentors/faculties、Identity 和 GroupX 角色映射到精确 RoleRef。
- 建立 Goal 附着式 SupervisionPolicy、Assessment 和 Deliberation 事务。
- 实现确定性停滞信号与可选 LLM 评估。
- 在显式授权和预算内调用 GroupX CouncilService。
- 将 Decision Artifact 有界地加入下一 Goal Round，并确保模型可见内容可由会话日志重建。
- 保留现有非 Goal advice/takeover、Handoff、分配和矩阵能力的兼容路径。
- 提供独立 Store、迁移 dry-run、API、Client UI、审计、卸载和恢复演练。

### 5.2 本项目不做

- 不创建第二套 Goal phase、objective 或 Round 数据库。
- 不让 Supervisor 在 active Goal 期间调用普通 `agent.followup()` 驱动续行。
- 不让学院和 Group 共享同一个运行成员对象。
- 不自动发现或启用用户未选择的 Provider、模型、Agent 或工具。
- v1 不给 Council 成员工作区写权限、shell、网络或凭据访问；成员为 `llm-only/advice-only`。
- 不把原始会话日志、Group 完整讨论、Prompt 正文、凭据、环境变量或私有路径返回 Client。
- 不自动完成 Goal；完成仍由 Goal Round 中的模型工具或明确用户操作决定。
- 不替换 DSH Session、Agent Preset、模型目录、Handoff 或 GroupX 自有运行状态。
- 不在首次实验中修改生产 Profile、已安装应用或 shipped preset。
- 不在本规划阶段创建远程仓库、发布包或推动生产升级。

## 6. 核心用户场景

### S1：给现有 Goal 开启智能监管

用户通过官方 Goal UI/API 创建目标，再确认至少一条 success criterion 并在 Supervisor 面板附着 SupervisionPolicy。系统可草拟 criteria，但未获用户确认不能激活 policy。Goal 继续由原生 Driver 驱动；Supervisor 从下一 Round 开始提供进展评估。

### S2：目标正常推进

每轮结束后，Supervisor 从持久 Goal、todo 变化、工具结果类别、验收证据和历史 Assessment 构建新证据。若确认取得进展，下一 Round 只收到简短进展与剩余成功标准，不召集 Group。

### S3：目标停滞，建议模式请求讨论

相同 blocker 或无新证据连续达到阈值后，Supervisor 显示建议召集的角色、候选成员、预计调用和超时。用户确认后才创建 Deliberation。

### S4：目标停滞，智能接管自动讨论

用户已显式选择 bounded-auto，并批准候选池与预算。停滞达到阈值后，Supervisor 先冻结 exact ParticipantPlan，再自动创建一次幂等 Deliberation；只能从 current 候选池选人，不能替换、减员、扩员或扩大权限。

### S5：GroupX 缺失或失败

Supervisor 记录 `council-unavailable` 或稳定失败码，继续原生 Goal Round，并提供单 Supervisor 的降级建议。界面不得显示“已达成共识”。

### S6：讨论有分歧

Decision Artifact 明确保存综合建议、不同意见、证据缺口和停止原因。Council v1 只有 `advisory/unresolved`，不得把多数意见包装成用户批准、正式结论或“已达共识”。

### S7：人类消息与自动准备竞争

Driver 在 before-next-round maintenance 中准备讨论时，用户消息会立即 abort preparation，禁止创建 reservation；maintenance 退出后先处理人类输入。旧 generation 不得提交或影响该 human turn，下一 Goal Round 必须重新检查 exact GoalRef、round 和 deliverTo。

### S8：重启与恢复

DSH 重启后，原生 Goal 保留但 activation 按原生规则停用；Policy、Assessment、Deliberation 与稳定 GoalSubject 的预算恢复为 suspended。用户恢复同 goalId 后，phase-only revision 自动 rebind policy、停滞窗口清零且历史/总预算保留；bounded-auto grant 不跨 revision，必须重新授权。

### S9：关闭新功能

禁用 Supervisor v2 或 Council Provider 后，原生 Goal Driver 仍按 stock 行为工作；旧分配、设置、Handoff 和会话日志不丢失。

### S10：从旧学院配置迁移

运维先执行 dry-run，看到每个 mentor/faculty 的目标 RoleRef、alias、Prompt digest 和冲突。只有完整、无歧义的映射可提交；失败项继续使用 legacy 适配层。

## 8. 非功能需求

| ID | 需求 | 指标/边界 |
| --- | --- | --- |
| NFR-001 | 安全 | 不弱化沙箱、审批、工具或凭据策略；Council v1 无工具权限 |
| NFR-002 | 确定性 | exact RoleRef、CAS GoalRef、generation、correlation key、ParticipantPlan 与 receipt digest 均可重放 |
| NFR-003 | 有界数据 | API body ≤64 KiB；批量 session ≤200；模型监督上下文默认 ≤4,000 字符且可配置 |
| NFR-004 | 有界自治 | 默认最多 2 次讨论/Goal、4 名参与者、12 次成员调用；手动讨论 120 秒，自动 before-next-round 最多阻塞 45 秒；全部为可验证配置项 |
| NFR-005 | 故障隔离 | Role、Council、矩阵或可选 UI 失败不阻止 stock Goal 和 DSH 启动 |
| NFR-006 | 持久恢复 | 原子写入；重启后不得把 `dispatching` 猜成 `resolved`，必须显式恢复/失败 |
| NFR-007 | 生命周期 | 注册、timer、listener、style、Slot 和任务均由 Cordis fiber disposer 拥有 |
| NFR-008 | 并发 | 每 session 只有一个 preparation generation；旧异步结果不得提交 |
| NFR-009 | 可观测 | 稳定错误码、阶段、耗时、预算使用量和降级原因可查；不输出原始日志 |
| NFR-010 | 兼容 | 精确锁定目标 DSH/Cordis/GroupX 版本；缺 peer 依赖时明确失败或局部降级 |
| NFR-011 | UI | 键盘可操作、light/dark、reduced-motion；状态刷新不改变主要几何 |
| NFR-012 | 发布安全 | manifest、lockfile、Git、远端、tarball 与隔离 Profile dry-run 一致后才可发布 |

NFR-004 的数字是已批准默认值，不是协议常量；实现时必须放入经过验证的配置字段。

## 9. 权限与数据边界

### 9.1 用户授权

- Goal 创建、编辑、暂停、恢复和清除继续走官方 Goal API/命令。
- Supervisor 不能把 plugin 消息伪装成 `{ kind: 'user' }` 获取 Goal 权限。
- `guided` 只提出讨论请求；`bounded-auto` 必须由用户显式开启，并保存授权来源、候选快照和预算。
- 自动讨论不意味着自动扩大工具、文件、网络或模型权限。

### 9.2 Host/Client

- Role Prompt、Assessment 输入、完整 Decision Artifact 内部字段、Session/Context/Service 对象留在 Host。
- Client 只接收公开角色元数据、状态枚举、短摘要、预算和稳定错误码。
- Host↔Client、Supervisor↔Council 的业务协议为 JSON-only；同进程 Council 只额外接受独立 `AbortSignal` 生命周期参数，不传 live Context/Agent/Session，跨进程实现改用 opaque cancellation token。

### 9.3 持久化

- 原生会话日志拥有 Goal 变更和所有模型可见 Goal Round 内容。
- `smart-supervision.v1.json` 只保存策略、Assessment、Deliberation、预算与有界审计。
- 现有 `supervisor-state.v1.json` 保持原格式，v2 不原地提升版本。

## 10. 停滞判定

第一版采用“确定性信号优先，LLM 评估补充”的规则。以下条件本身不能构成停滞：任务复杂、模型表示不确定、单次工具失败、尚有可执行工作或只剩较少 Round。

可计入停滞的信号：

- 相同规范化 blocker 在连续 Goal Round 中重复出现；
- todo/验收证据 digest 连续多轮无变化，且没有新的成功工具证据；
- 同一验证项在执行修复后连续失败；
- Goal Round 明确报告缺少某项能力或证据，且当前角色集合无法覆盖；
- 上下文健康度进入 aging/handoff-recommended，但仍未生成可用 Handoff。

默认达到三个连续无进展 Round 才建议讨论；默认冷却两个 Round 后才允许再次自动讨论。所有阈值必须可配置并进入审计。结构化能力缺口可以立即生成“建议讨论”，但 bounded-auto 仍必须满足用户授权与独立自动触发阈值。

## 11. 失败模式与期望行为

| 失败 | 期望行为 |
| --- | --- |
| Role Core 缺失 | Supervisor 使用 legacy 显示与单导师降级；禁止自动 Council |
| RoleRef 版本缺失 | 拒绝该绑定并提示重新选择；不自动选择 latest |
| Council Provider 缺失 | 记录 `council-unavailable`，继续 stock Goal |
| 个别成员失败 | 结果标记 member failure；是否继续由 Council 协议决定 |
| 全员失败/超时 | Deliberation 失败或超时；不显示共识；Goal 继续或由用户暂停 |
| 预算不足 | 不开始半轮讨论；返回 `budget-exhausted` |
| 用户在准备期间发消息 | 人类输入优先；旧 preparation 失效或只保留审计 |
| Goal revision 改变 | 拒绝旧结果提交；重新评估新 ref |
| before-next-round 监听抛错/超时 | Driver 记录安全诊断并 fail-open 走 stock queue；监听错误绝不使 Goal disarm |
| runtime-context 被 Profile 禁用/抑制 | 标记 `context-unavailable`，禁止 bounded-auto 消费 Council 预算；Goal 继续 |
| 持久化失败 | 不启动自动讨论；stock Goal 可继续，界面显示降级 |
| Supervisor 卸载 | 清理监听和上下文；stock Goal Driver 保持可用 |
| 重启发生在 dispatching | 恢复为需要 reconcile 的状态，不猜测远端完成 |

## 12. 成功标准

项目只有同时满足以下条件才算完成：

1. active Goal 压测中 Supervisor 注入的普通续行消息为 0。
2. Supervisor 缺席、失败或卸载时，stock Goal transcript 与基线一致。
3. 每次自动讨论都能追溯到显式授权、确定性停滞信号、current 候选池、exact ParticipantPlan 和预算。
4. 任一 RoleRef 可证明精确版本与 digest；Prompt 从不通过浏览器 API 返回。
5. Decision Artifact 的分歧、失败与证据缺口不会被包装成共识。
6. 重启、取消、并发人类消息和 Goal edit 均不会重复创建讨论或消耗重复 Round。
7. 禁用 v2 行即可恢复 stock Goal，现有 assignment、Handoff 与 Session 保持完整。
8. 自动化、隔离 Web、真实 Desktop、卸载/重载、恢复演练和秘密扫描全部通过。
9. manifest、lockfile、本地 Git、远端 Git、制品和运行时 dry-run 指向同一精确版本。

## 13. 已证伪或拒绝的方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| Supervisor 自建完整 Goal 状态机 | 拒绝 | 与原生 Goal phase/revision/Round 产生双真源 |
| active Goal 时继续使用 watchdog followup | 拒绝 | 两个续行调度器竞争，可能重复 Round |
| MVP 替换或 fork Goal Round Driver | 拒绝 | 需要复制 checkpoint、reservation、竞争输入、取消、disarm、pre-step 校验和卸载协议 |
| 把 `agent/turn-stopping` 当作最终 Round 边界 | 拒绝 | 其他 Stop hook 可 steer 后重复触发，会提前评估或重复消费预算 |
| MVP 修改固定 Goal Round prompt | 拒绝 | 现有 invariant 按固定 renderer 重建并验证持久前缀 |
| 学院与 Group 共用成员对象 | 拒绝 | 生命周期、模型故障、权限和会话状态会互相污染 |
| 让 dsh-groupx 独占全局角色库 | 拒绝 | Identity/Supervisor 反向依赖可选 Council 产品 |
| 让 dsh-supervisor 独占角色库 | 拒绝 | GroupX 和 Identity 无法独立加载或贡献角色 |
| Client 保存业务状态/Prompt | 拒绝 | 刷新丢失、泄露 Prompt、违反 Host 权威原则 |
| 缺 GroupX 时伪造多导师共识 | 拒绝 | 无真实参与和协议，输出会误导用户 |
| 直接 bump Supervisor v1 Store | 拒绝 | 当前未知版本加载路径会返回空状态 |
| 直接在生产 Profile 开发 | 拒绝 | 缺少隔离、回滚和失败边界 |
