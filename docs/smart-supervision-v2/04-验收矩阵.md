# DSH Smart Supervision v2 验收矩阵

> 状态：验收基线已批准（2026-08-27）；P0 本地门槛已于 2026-08-28 执行，本矩阵仍不授权 P1/P2、运行时变更、推送或发布。

## 1. 文档目的

本矩阵把需求、架构约束和 P0～P10 开发阶段转换为可执行的验收门槛。它用于阶段开工、阶段收口、跨仓集成和最终发布判断，不授权实现、提交、推送或发布。

本文中的命令名是拟建立的稳定验证入口；P0 必须依据恢复后的工程真源确认或调整脚本名，并同步回写本文。任何阶段不得以“手工看起来正常”替代可重复验证。

## 2. 验收原则

1. **先保 stock Goal，再加监管能力**：未安装或关闭 Supervisor 时，Goal 行为必须与基线一致。
2. **一项事实只有一个权威来源**：Goal、Role、Policy、Council 各自按架构所有权验收。
3. **正向与反向同时验证**：既验证该发生的行为，也验证未授权、未匹配和超预算时绝不发生。
4. **自动化优先，真实运行时收口**：单元测试不能替代隔离 Profile 中的真实 DSH 验收。
5. **证据最小化**：保留摘要、哈希、测试结果和脱敏截图，不保留原始聊天、原始工具输出、凭据或私有路径。
6. **失败关闭且可降级**：RoleRef 无法精确解析、授权不足或预算不足时拒绝新动作；可选组件失败不得阻塞 stock Goal。
7. **阶段独立可回滚**：每阶段都必须证明禁用或移除新增行后可以回到上一阶段行为。

## 5. Given / When / Then 关键场景

### C01：stock Goal 对照

- Given：同一隔离 Profile 分别安装和不安装 Supervisor，使用相同 Goal 配置与确定性 fixture。
- When：运行一个无需监管的正常 Goal。
- Then：Goal Round 数、生命周期事件和最终状态一致；新增系统只产生允许的监督审计，不产生续行调用。

### C02：active Goal 阻断旧调度路径

- Given：session 有 active Goal，watchdog 和旧 event hook 同时满足触发条件。
- When：两条路径同时执行。
- Then：统一 gate 拒绝 Supervisor 调度，`followup`、`steer`、`inject` 均为零调用；原生 Goal Driver 仍可正常续行。

### C03：候选停止点重复但最终 seam 唯一

- Given：Goal A 的同一 turn 先触发 turn-stopping，另一个 Stop hook `steer()` 后再次 stopping，同时存在 wrong GoalRef/round fixture。
- When：该 turn 最终提交，Driver 完成 checkpoint 并准备下一 Round。
- Then：provisional stopping 不产生最终副作用；只为匹配 messageId/turn/turnEndSeq 的 before-next-round correlationKey 创建一次 Assessment，其余事件不改变预算或 discussion。

### C04：动态上下文可重放

- Given：Goal A 有 pending Delivery，另一个动态 context 会变化；覆盖 bind 前/后、snapshot admitted 前/后的 crash。
- When：初始或 resume 后 `completed=undefined` 的 queue candidate 绑定 delivery，Goal turn 因 steer 有多个 step，期间再插入 human claim、compaction/replay。
- Then：每个目标 Goal step 的最新 snapshot 只含一个冻结 supervisor section；human turn 为零；crash 后按日志在 pending/bound/admitted 间确定恢复，不重复消费；固定 Goal prompt 不变。

### C05：停滞阈值的正反例

- Given：默认 `unchangedRounds=3`。
- When：先连续产生 2 个无进展 Round，再产生第 3 个；另一路在第 3 个前出现有效进展。
- Then：第一路只在第 3 个触发；第二路清零或推进窗口，不触发讨论建议。

### C06：guided 模式

- Given：用户明确启用 guided，停滞阈值满足，预算充足且 Council Provider 可用。
- When：评估建议讨论。
- Then：seam 原子创建 stable RecommendationRecord 且不阻塞下一 Round；accept/decline 时 Provider 调用数为 0。用户若要讨论，须 accept-awaiting-pause、调用官方 pause/disarm，再用 exact recommendationId+assessmentId+manualRequestId 显式 request；拒绝后同 assessment/generation 不再建议。

### C07：bounded-auto 模式

- Given：用户明确授权 bounded-auto，并冻结候选 pool、exact ParticipantPlan 和预算。
- When：停滞阈值、冷却、context capability、下轮 capacity 和预算条件同时满足。
- Then：系统在 45 秒 preparation deadline 内最多创建一次幂等 discussion；不得替换、减员、扩员、换模型或增权，receipt/result 必须匹配 planDigest；结果只进入 exact next Goal Round。插入人类消息会 abort，Goal reservation 为 0；BudgetReservation 在 dispatch receipt 前释放，receipt 后先 accepted 并保留完整 calls 占用，再按 usage/保守规则 settled。

### C08：预算或授权不足

- Given：分别缺少用户授权、grant revision 陈旧、达到讨论/调用数、处于冷却期、无下轮 capacity 或 runtime-context 被抑制。
- When：停滞检测再次命中。
- Then：Council Provider 均不被调用，并产生稳定、可解释的拒绝或等待原因；manual-at-cap/blocked/complete 时 BudgetReservation 与 DeliveryRecord 也均为 0。

### C09：Provider 缺失或失败

- Given：GroupX/CouncilService 未安装、超时或返回部分失败。
- When：请求 discussion。
- Then：Supervisor 降级为单一建议或显式失败；只显示 advisory/unresolved，不伪造共识；listener 错误 fail-local，不使 Goal disarm。

### C10：dispatching 中重启

- Given：discussion 已进入 dispatching，但尚无已确认结果。
- When：Host 异常退出并重启。
- Then：系统按 Provider 能力执行显式恢复、查询或 failed_retryable 收口；Host 在 Provider 接受后、receipt 落盘前 crash 时用同 key/attempt 找回同 receipt 并转 accepted，绝不释放后重派或直接标记 resolved；无法证明 calls 时按预留全额结算，同一 reconcile 不重复扣费。

### C11：角色定义共享、成员实例隔离

- Given：学院 Actor 与 GroupX Actor 绑定同一 exact RoleRef。
- When：两者分别运行并更新自身会话、模型和 discussion 状态。
- Then：解析出的 RoleDefinition digest 相同，但 ActorRef、成员状态、预算和会话完全隔离。

### C12：Prompt 保密

- Given：RoleDefinition 含 Host-private prompt 和可公开展示字段。
- When：调用 list/public API、构建 Client、记录审计并打包 tarball。
- Then：Client/public/API/Store/日志/审计只有 PublicRole/RoleRef/digest，Prompt 零泄漏；Host tarball 可含已审查的版本化 Prompt，但 Client entry/chunk、secret、私有路径和 raw log 零命中。

### C13：legacy dry-run

- Given：旧 mentors/faculties、Identity prompt 和 GroupX 九角色含可映射/未知项；FR-023 included 时再加入 HARVIS roster。
- When：连续执行两次 dry-run，再选择性应用已确认映射。
- Then：两次报告完全一致并列出 exact ref、alias、Prompt/overlay digest 和冲突且不含正文；dry-run 不改旧 Store；Identity Prompt 保真，九 alias 逐项正确，未知项保持原状。

### C14a：运行时关闭与逻辑卸载恢复（P9）

- Given：一个 Goal 已附着 policy，分别执行 Cordis stop/unload 和 Loader row disable/enable。
- When：Goal 继续，再重新启用 Supervisor/GroupX。
- Then：stock Goal 正常；无 provider/listener/task/Service 残留；旧 Store 不删除，重新启用后以 suspended/reconcile 规则恢复，grant 不自动恢复。

### C14b：物理移除与 cold start（P10）

- Given：已记录精确安装制品和 Store，物理移除 Supervisor/GroupX package。
- When：执行 cold start、运行 stock Goal，再恢复同一批准制品并二次 cold start。
- Then：缺包时 stock DSH 正常且无 stale Slot/Service/context；Store 保留但不被未知代码改写；恢复后按 suspended/reconcile 规则加载，grant 不自动恢复。

### C15：Goal 与 Policy 生命周期

- Given：同一 Goal 依次 pause、restart、phase-only resume、objective edit、block、complete/clear。
- When：每次状态变化后读取 Policy、历史和 generation。
- Then：pause/restart/block suspended；phase-only resume rebind policy且窗口清零；语义 edit review-required；complete/clear closed；任何旧异步结果提交数为 0。grant/预算另见 C18。

### C16a：Goal seam 与 context 故障隔离（P4）

- Given：分别让 before-next-round listener、Smart Store 和 runtime-context provider 抛错，并让 runtimeContextCapability 返回 unknown/false。
- When：stock Goal 准备下一 Round。
- Then：普通监听错误/timeout 与 checkpoint flush 故障均 fail-local 且 Goal 不 disarm；context provider 同步 catch；capability unknown/false 时 auto-admission gate 为 false，UI/审计显示稳定降级码。

### C16b：Evaluator 故障隔离（P5）

- Given：可选 evaluator 分别 timeout、抛错、返回越界或非法 schema。
- When：final Assessment 需要补充 unknown 信号。
- Then：本 Round 不重试，Assessment 以 unknown/degraded 收口，Recommendation 不被伪造，stock Goal 继续。

### C16c：Council 与 capability 竞争故障（P6-P7）

- Given：Council plan/dispatch/result 分别失败，或 runtimeContextCapability revision 在 reservation/dispatch 前变化。
- When：manual 或 bounded-auto discussion 进入准入与执行。
- Then：receipt 前释放 reservation；receipt 后按 usage 或全额保守结算；planDigest 不匹配不交付；capability stale 的 bounded-auto dispatch/预算消费为 0，stock Goal 不 disarm。

### C17：单 Host writer

- Given：相同 Profile 有重复 Loader row，或 HMR 新实例在旧 fiber 未 dispose 前注册。
- When：第二个 Supervisor Service 尝试挂载。
- Then：第二实例以 `SUPERVISION_INSTANCE_CONFLICT` fail closed，不能打开 Store writer、listener、timer 或 Coordinator；旧实例继续或按更新流程 drain。

### C18：Grant 与预算跨 revision

- Given：P6 已有 charged/reserved ledger，P7 签发 exact grant，随后发生 pause、restart、resume、policy/candidate/context-capability revision 和 budget amendment。
- When：分别尝试自动派发、撤销、重复 authorize/revoke 与提高总额度。
- Then：历史 reservation 永不重置；缺 ledger 的第一条合格请求只 CAS 创建一次；reserved 与 accepted 各只贡献一整笔，settled 按实际/保守值贡献，released 为零，任一时刻推导余额守恒；任一 revision/restart 使旧 grant 失效；普通 policy update 不扩额；只有显式 budget amendment 可提高且不能低于 committed 容量；所有重复动作幂等并审计。

### C19：人类输入消费 pending completion

- Given：Driver 已有一个 final pendingCompletion，并在 before-next-round 的可取消测试 listener 中准备。
- When：用户 nextTurn 入队并 abort preparation，在 checkpoint 前/后分别 crash，再让 human turn 完成并使 Goal 再次 queue。
- Then：append 后必须 await `ctx.sessions.flush()`；flush 后再次重检，期间出现 human 时追加并 flush superseded-consumed。durable checkpoint 或后继 durable human/ordinary boundary 证明原 completion 已消费；flush 前 crash 只以同 correlation 幂等重放，flush 后 crash 不重复；Goal reservation 为 0，human 后 queue 使用 `completed=undefined`，只重绑有效 Delivery。

### C20：手动讨论来源与交付

- Given：一个已 accepted 的 Recommendation 和一个没有 Assessment 的 direct-user 请求，均使用 paused/disarmed Goal、current candidate 与不同 manualRequestId。
- When：分别 request、重试同 payload、提交冲突 payload，并把结果绑定到 resume 后 Goal Round。
- Then：recommendation 分支校验 exact recommendation/assessment/decision 并使用 immutable recommendedIssue；direct 分支保存 direct-manual DeliverySource、不伪造 assessmentId；同 payload 幂等、冲突 409，两者只向 exact Goal turn 交付。

## 8. 证据包规范

每阶段建立一个不含敏感信息的证据目录或 CI artifact，最少包含：

```text
evidence/<stage>/
  manifest.json          # 阶段、commit、包版本、环境版本、结果摘要
  checks.json            # 每个验收 ID 的 pass/fail/skipped 与原因
  tests-summary.txt      # 测试计数和失败名称，不含原始对话/工具输出
  digests.json           # schema、fixture、bundle、tarball 等哈希
  screenshots-index.md   # 仅 UI 阶段；指向脱敏截图
  rollback-result.md     # 回滚或禁用验证结果
```

证据包不得包含：token、cookie、`.env` 值、访问文件内容、原始聊天、原始模型 prompt、完整工具输出、用户目录或机器私有绝对路径。需要定位问题时使用稳定 fixture ID、event ID、digest 和仓库相对路径。

## 9. 最终验收判定

最终结果只有三类：

- **通过**：优先级 P0/P1 的需求、选定的优先级 P2 范围和 NFR 门槛全部通过，无未处理高风险项。
- **有条件通过**：仅用户明确接受的优先级 P2 或非发布阻断项未完成，且不影响 stock Goal、安全、数据边界和恢复。
- **不通过**：出现双调度、Prompt/凭据泄漏、不可恢复状态、无界自治、伪造共识、版本漂移或发布闭环不一致中的任一项。

“有条件通过”不得用于绕过安全、授权、Goal 唯一调度、持久恢复或发布一致性门槛。
