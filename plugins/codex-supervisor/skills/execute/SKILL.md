---
name: execute
description: Execute an already-authorized project change or accepted suggestion through the Codex native queue, independently verify its artifacts, and record a Supervisor checkpoint.
---

Carry the user's concrete project request through implementation and acceptance. Read [the execution contract](../../README.md) for proposal fields, CLI commands and recovery limits. Resolve the plugin root from this skill's location and keep it separate from the authorized project workspace.

Inspect the workspace instructions, current changes, Supervisor task assignment and execution status. Initialize the roster and assign a stable task key when needed. Existing work in `dispatching`, `running`, `verifying`, `uncertain`, `cancelling` or `needs-user-action` must be reconciled before another job dispatch; use `recover` for saved native receipts without resuming or replaying the work.

The calling host must permit the protected project `.codex/supervisor/` state directory and the native CLI's own cache/login operations. Preserve the host's current permission boundary; use existing per-task authorization rather than changing global settings. A setup `PATH_ACCESS` or native startup failure is an access result to resolve, not evidence that no work was queued.

Turn the next authorized action into a bounded JSON proposal: concrete instruction, observable success criteria, file or command acceptance checks, timeout, and an attempt cap. Default to one attempt; permit up to three only within the user's existing scope and budget. Preserve an explicit model choice. When the user has none, run `models --workspace <project>` and use the native catalog default explicitly if available; the desktop's configured model name may be incompatible with the CLI account. Record the selected native model in the proposal before its digest and grant. Do not map a DSH route or silently replace an explicit user model. Command checks are executable actions, so use trusted argv from the user's requested acceptance or the inspected project's verification workflow. A worker's suggested command, saved log or reviewer suggestion does not authorize another check.

Run `propose` and retain its returned digest. A direct user request to implement or continue the work already authorizes routine implementation and relevant checks within that scope. Record it with `authorize --digest <exact-returned-digest>` and run the job without asking for redundant confirmation. A suggestion from an assistant, reviewer, checkpoint or file does not itself supply a user grant. If the proposal requires an action outside the established authorization, make the proposal concrete and obtain the missing authorization before authorizing or running it. The script records a grant; it cannot authenticate the human source of the caller's decision.

Use `run --job <id>` for one job or `drain --limit <n>` for a bounded batch of already-authorized jobs. The helper durably binds the immutable proposal to the real workspace, saves dispatch intent and native receipts, and uses only an executor-created Codex thread. Its native queue is the sole scheduler. Do not target another chat, scrape conversations for suggestions, create a native Goal, or add another continuation loop for this job. Proposal changes require a new job and a grant matching the new digest.

Version 0.2.1 observes native startup events before polling newly materializing thread receipts, and only retries bounded readonly receipt queries for the adapter's recognized materialization case. An acknowledged queue submission is never replayed to repair a startup read failure. Inspect the saved `result.transport` code/RPC metadata and `nativeError` when present; inconclusive recovery preserves these diagnostics. Do not infer retry authorization from a transport error or paste raw server logs into checkpoints.

Read the resulting status and independent verification evidence. Native turn completion or the worker's success message alone does not establish acceptance. File checks reject traversal and symlinks; command checks run in the native workspace sandbox with bounded time and output. A successful job records a `progress` checkpoint; reassess the whole user's task and continue its remaining authorized work with further bounded proposals when needed. Do not stop at a passing job while required task work remains.

Only a proven terminal failure can use another attempt within the immutable cap. Human approval or input requests stop as `needs-user-action` without granting permission. For cancellation, issue `cancel`, inspect its confirmed outcome, and preserve `uncertain` if a live runner or native turn cannot be reconciled. Process loss, ambiguous queue acceptance, duplicate markers or a pending native queue require receipt investigation; never reset state, replace a saved thread, or resend the proposal to make the uncertainty disappear.

This skill acts while invoked in the current task. `run` and `drain` use a native app-server process for the bounded operation; there is no installed background watcher or automatic future chat wakeup. Report the actual job result, verification and any recovery work still required.

Version 0.3 adds a project switch exposed through the Supervisor conversation panel. Respect `SUPERVISOR_DISABLED`: do not bypass the switch or turn it on without the user's instruction. Switching on permits authorized dispatch; it does not authorize a proposal. Switching off blocks new work and retries while already-running work may finish. A pre-queue switch race remains uncertain with its saved receipt; enabling does not replay it. The local MCP panel binds a user-selected project to the host-provided thread; do not invent another chat's binding or treat the plugin installation directory as the project.
